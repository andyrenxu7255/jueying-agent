# DEV-23 AI 原生运营系统总纲

> 状态：研发总纲
> 读者：内部产品、研发、架构、Agent 实现团队
> 依据：2026-05-25 AI 应用场景分享会议转写、后续产品讨论

## 1. 北极星

升级后的系统不是传统项目管理工具，也不是单纯的 Agent 编排平台，而是面向中小企业的 **AI 原生运营系统**。

它的目标是让企业中的任何事项都能被 AI 持续管理：AI 理解目标，拆解任务，识别信息缺口，指导人类采集现场信息，调度 Agent 或人类执行，检查交付物，推动状态流转，并形成复盘和组织经验。

最关键的变化是：AI 不再只是人调用的工具，而成为运营推进的主体。人类不默认承担日常管理中的所有判断、催办、检查和复盘，而更多承担意图给定、现场信息采集、物理执行、责任确认和高风险边界控制。

## 2. 核心判断

顶尖模型驱动的 Agent 在结构化判断、推理、总结、比较、计划和调度上，可能已经超过绝大多数普通人类管理者。产品设计不能再默认“人判断、AI 辅助”，而要承认 Agent 可以在大量日常运营判断中成为更稳定的主体。

Agent 当前最大的困境不是判断能力本身，而是信息获取不足，也就是 **传感器不足**。它缺少人类天然具备的传感器：听、看、触摸、闻到气味、感受温度、捕捉现场微妙变化、理解非结构化环境。因此，闭环中的人类经常不是最终决策者，而是 Agent 的信息采集协作者。

正确的人机分工应是：

- 人类提供经营意图、约束、责任边界和现场信息。
- Agent 说明缺什么信息、为什么缺、谁去采、怎么采、按什么格式反馈。
- 人类按 Agent 的信息采集要求完成观察、拍照、拜访、询问、记录、确认现场事实。
- Agent 基于补齐后的信息做判断、派生任务、推进状态和复盘。
- 高风险、不可逆、法律/财务/人事等责任节点由人类确认。

信息永远无法穷举，过量信息也会被人类忽略和遗忘。系统的价值不是追求万能，而是在已有管理方向和框架下，让 Agent 以更细颗粒度、更高频次、更稳定的方式推进事项。

## 3. AI 主体不等于无人治理

“AI 为运营主体”必须配套自治等级，否则会在落地时混淆责任和权限。

| 等级 | 名称 | 行为边界 |
|---|---|---|
| L0 | 建议模式 | Agent 只分析和建议，人手动创建任务和推进。 |
| L1 | 确认后派发 | Agent 拆解任务和计划，经人确认后派发。 |
| L2 | 自动派发，关键验收 | Agent 自动派发和催办，关键节点由人验收。 |
| L3 | 异常升级 | Agent 自动推进日常闭环，只把异常、高风险、低置信度事项升级给人。 |
| L4 | 事后审计 | Agent 在授权范围内自动闭环，人主要做抽查和审计。 |

JueYing 的初期升级不应追求 L4，而应先稳定实现 L1-L3：让 AI PM 能真实管理一件事，并把信息缺口、任务状态、验收证据和异常升级讲清楚。

## 4. 对象模型

会议中“项目”被用作广义的“一件事”。产品建模时不能把所有对象都叫 Project，否则会造成模板、实例、周期事项和任务图谱混乱。

推荐对象模型如下：

| 对象 | 定义 |
|---|---|
| Work Unit | 可被 AI 管理的一件事，是最高抽象。 |
| Project | 有明确目标和终点的一次性事项，例如客户交付、产品研发、营销活动。 |
| Routine | 周期性运营事项，例如每周卫生检查、每日销售跟进、月度回款复盘。 |
| Run | Project 或 Routine 的一次执行实例。 |
| Task | 可验收的执行颗粒度，是运营系统的核心单元。 |
| Action | Task 内部更细的动作，可选。 |
| Assignment | Task 派给某个 Agent、数字分身或真人后的执行记录。 |
| Deliverable | Task 或 Project 的交付物。 |
| Evidence | 证明任务状态或交付质量的证据，例如照片、会议纪要、客户反馈、文件、链接。 |
| TaskGraph | 表达任务、依赖、并行、状态、交付物和验收规则的动态施工图谱。 |
| External Fact Mirror | CRM、项目管理系统等外部业务系统事实的本地快照。 |
| Writeback Intent | Agent 向外部业务系统反写前生成的可审计意图。 |

`TaskGraph` 不是传统甘特图，也不是线性 workflow stage list。它必须能表达依赖、并行、动态新增、重规划、提前/延后、信息缺口和验收状态。

外部 CRM 和项目管理系统不应被新系统默认替代。它们是企业已有业务事实层；Agent 层维护的是运营判断事实。两者必须通过 Mirror、Writeback Intent、Policy、Queue 和 Audit 保持一致，不能把 CRM 阶段、外部项目任务状态直接等同于 Agent 的 Gate 判断或 TaskGraph 状态。

## 5. Agent 组织

| Agent | 职责 |
|---|---|
| COO Agent | 企业级运营观察者，跨 Program/Project/Routine 发现风险、机会、资源瓶颈和优化建议。 |
| Program Manager Agent | 管理一组相关 Project/Routine，例如“提升线索获取效率”。 |
| Project Manager Agent | MVP 核心角色，负责理解目标、生成 TaskGraph、派发任务、推动状态、处理异常和复盘。 |
| Worker Agent | 直接完成 AI 可做的任务，例如写文案、做分析、生成方案、写代码、整理报告。 |
| Human Twin Agent | 真人的数字分身，是人的信息接口、提醒助手、反馈整理者和授权代理。 |
| Skill | Agent 可调用的能力，包括提示词、工具、MCP、流程模板、知识和岗位经验。 |

产品表达中不应说“人是 Agent 的工具”。更准确的表达是：真人是责任主体和现场执行者，数字分身是系统内可调度、可提醒、可结构化反馈的信息接口。

## 6. Human Twin Agent 权限边界

数字分身必须有明确授权等级：

| 权限 | 含义 |
|---|---|
| notify | 只能提醒真人和转述任务。 |
| collect | 可向真人追问信息，并按 schema 整理反馈。 |
| draft | 可生成草稿、建议和初步交付物。 |
| submit_with_confirmation | 真人确认后提交结果。 |
| act_delegated | 在明确授权范围内自动行动。 |

系统默认应从 `notify + collect + draft` 开始，避免数字分身在未经授权时替真人做承诺、确认完成或提交高风险结果。

## 7. 信息采集闭环

AI 原生运营系统的关键能力不是“让人填表”，而是让 Agent 主动提出信息缺口。

标准闭环：

1. Agent 理解目标。
2. Agent 生成初始 TaskGraph。
3. Agent 判断当前信息是否足以推进。
4. 如不足，Agent 生成信息采集任务。
5. Human Twin Agent 通知真人：缺什么、为什么缺、如何采、格式是什么、截止时间是什么。
6. 真人采集现场信息并反馈。
7. Human Twin Agent 结构化整理、检查完整性，必要时追问补充。
8. Project Manager Agent 基于新信息判断、验收、派生任务或重规划。

这条链路应成为 JueYing 升级的核心产品体验。

## 8. MVP 闭环

最小可用闭环不需要复杂行业场景。一个“每周五办公室卫生检查”就足够验证 AI 原生运营。

MVP 应能做到：

- 创建一个 Routine。
- 指定 Project Manager Agent。
- 指定可用人员及其 Human Twin Agent。
- Agent 自动拆解检查任务。
- Agent 说明每个任务需要什么证据，例如照片、评分、问题描述。
- 到时间自动提醒真人。
- 真人通过 IM 或任务界面提交信息。
- Human Twin Agent 检查信息是否完整。
- Project Manager Agent 验收并更新 TaskGraph。
- 系统输出本次 Run 的结果、异常和下次优化建议。

这个闭环验证的是“AI 管事”，不是“AI 替人做所有事”。

## 9. 反模式

- 不要把系统做成全局甘特图。甘特图只能表达时间，不足以表达动态任务图谱和信息缺口。
- 不要把现有 workflow stage list 直接改名为 TaskGraph。线性阶段链不是运营图谱。
- 不要把所有事项都叫 Project。需要区分 Project、Routine、Run、Task。
- 不要让 Agent 无限自治。必须有自治等级、授权边界和异常升级。
- 不要把人的角色压缩为“决策者”。在大量场景中，人更重要的是现场信息采集者和责任确认者。
- 不要把数字分身设计成权限黑洞。默认只能提醒、收集、整理、生成草稿。
- 不要把 CRM 或项目管理系统重做一遍。新系统应连接、镜像、校验和低风险反写，而不是替代客户原有事实层。
- 不要把外部系统状态当作 Agent 运营判断。CRM 阶段和外部项目任务状态只能作为输入事实，不能绕过 Gate、Evidence、Information Gap 和验收规则。

## 10. 对 JueYing 的升级含义

JueYing v1 的 workflow、skill、proactive、org_task、IM 接入和归因能力都可以复用，但它们不是最终产品抽象。

升级方向应是：

- 在 workflow 之上建立 Work Unit / Project / Routine / TaskGraph 运营层。
- 把 proactive 从“规则扫描派单”升级为 COO Agent 的信号发现组件。
- 把 org_task 从扁平任务派单升级为 TaskGraph 的人类执行通道。
- 把 skill-library 从技能库升级为 Agent 能力和岗位经验扩散机制。
- 把 Web Portal 从 Admin 控制台升级为 AI PM 配置、数字分身配置、任务施工图谱可观测和异常验收工作台。
